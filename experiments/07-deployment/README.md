# 07. 카나리와 블루그린: 원격 번들의 배포 전략

05에서 만든 host / feature 구조 위에 배포 전략을 얹은 실험입니다. 장바구니 피처의 v2 를 만들어 로컬 배포 서버에 두고, 블루그린 전환과 롤백, 카나리 비율 배포를 에뮬레이터에서 검증했습니다. 서버와 데이터는 전부 로컬 더미입니다.

네이티브 앱은 05 의 것을 한 줄도 안 바꾸고 그대로 씁니다. JS 번들과 서버 상태만 바뀝니다. 배포 전략이 앱 릴리스와 무관한 계층이라는 것이 이 실험의 첫 번째 결론입니다.

## 두 전략이 뭐가 다른가

**블루그린**은 슬롯 두 개(blue 안정판, green 후보판)와 포인터 하나입니다. 전환은 포인터를 green 으로 바꾸는 것이고, 롤백은 되돌리는 것입니다. 전원이 한꺼번에 같은 판을 봅니다. 전환도 롤백도 즉시라는 게 장점이고, 문제가 있으면 전원이 함께 맞는다는 게 단점입니다.

**카나리**는 후보판을 일부에게만 먼저 줍니다. 사용자를 0~99 버킷에 결정적 해시로 배치하고, 버킷이 비율(예: 30) 미만인 사용자만 green 을 받습니다. 0 → 5 → 30 → 100 으로 올리는 게 점진 배포, 문제가 보이면 0 으로 내리는 게 롤백입니다. 폭발 반경을 줄이는 대신, 지표를 볼 시간과 두 버전이 공존하는 기간을 감수합니다.

버킷 해시가 결정적이어야 하는 이유는 코드 주석에도 적었지만 중요해서 다시 적습니다. 같은 사용자가 재시작할 때마다 v1 과 v2 를 오가면 사용자에게는 버그로 보이고 지표에서는 두 집단이 섞입니다. Math.random 이 아니라 `hash(피처명 + 사용자id) % 100` 이어야 합니다.

## Re.Pack 에서의 구현: 결정 지점이 리졸버 하나

Re.Pack 구조에서 배포 전략이 들어가는 자리는 정확히 한 곳, ScriptManager 리졸버입니다.

```
deployment.json (서버, 배포 상태의 유일한 진실)
  { strategy: "canary" | "blue-green", blue: "v1", green: "v2",
    active: "blue" | "green", canaryRatio: 30 }

리졸버 (클라이언트, 시작 시 한 번 읽음)
  version = strategy 에 따라 결정
  url = /releases/featureCart/<version>/<platform>/<파일>
```

- 결정은 클라이언트에서 합니다. 서버는 정적 상태 파일과 정적 번들만 두면 되므로 CDN 에 그대로 올라갑니다. 사용자별 응답을 만드는 서버가 필요 없습니다. CodePush 와 같은 구조입니다.
- 결정은 세션당 한 번입니다. 화면을 보는 중에 배포가 바뀌어 화면 절반씩 다른 버전이 되는 것을 막는 가장 단순한 방법이고, 실서비스 OTA 들이 다음 콜드 스타트에 적용하는 이유와 같습니다. 05에서 확인한 federation 런타임의 모듈 캐시도 세션 중 교체를 막는 쪽으로 작용하므로, 구조와 제약이 같은 방향을 가리킵니다.
- URL 에 버전이 들어가므로 캐시 무효화가 공짜입니다. 새 배포는 새 경로라 자연히 캐시 미스이고, 이전 버전 캐시는 롤백 때 그대로 살아 있습니다.

v2 릴리스를 만드는 비용도 확인했습니다. 피처 디렉토리를 복사해 화면 코드만 바꾸고 같은 설정으로 빌드하면 끝입니다. 단, name 과 exposes 는 호스트와의 계약이라 버전이 바뀌어도 유지해야 합니다. 계약을 바꾸는 릴리스(노출 이름, props 변경)는 카나리로 점진 배포할 수 없고 호스트와 함께 나가야 합니다. 이게 이 방식의 실질적 경계선입니다.

## 검증한 것 (Pixel 9 에뮬레이터)

| 시나리오 | 결과 |
|---|---|
| 블루그린 active=blue | 전원 v1 배정, v1 컨테이너 152,315 bytes 다운로드, 초록 배지 |
| active=green 전환 후 재시작 | 전원 v2, v2 컨테이너 153,354 bytes 다운로드, 주황 배지 + 릴리스 노트 |
| active=blue 롤백 | 다시 v1. 서버의 포인터 한 줄로 왕복 |
| 카나리 30% | 10명 중 버킷 26, 7, 12 인 1, 2, 7번만 v2. 정확히 3명 |
| 같은 배포 상태에서 사용자만 교체 | 1번 사용자는 v2 를, 3번(버킷 88)은 v1 을 다운로드. 서버 로그로 확인 |

전환과 롤백 어느 경우에도 APK 는 재설치하지 않았습니다. 서버의 deployment.json 을 curl 로 바꾸고 앱을 재시작한 것이 전부입니다.

## granite 라면 어떻게 되나

granite 는 배포 파이프라인을 프레임워크에 포함합니다. `granite-forge deploy --bucket ...` 가 번들을 S3 에 올리고 CloudFront 에 얹는 것까지 해 주고, 인프라 자체도 pulumi 코드(`@granite-js/pulumi-aws` 의 ReactNativeBundleCDN)로 만들어 줍니다. 06에서 본 것처럼 셸의 BundleLoader 가 CDN 의 번들을 받아 실행합니다.

차이는 결정 지점의 위치입니다.

- Re.Pack: 결정 로직이 우리 손의 리졸버에 있습니다. 위에서 만든 카나리와 블루그린이 전부 클라이언트 JS 수십 줄입니다. 유연한 대신 전부 우리 책임입니다.
- granite: 업로드와 서빙은 forge 와 CDN 이 해 주지만, "누구에게 어느 버전을"의 라우팅 전략은 OSS 범위에 없습니다. 같은 것을 하려면 결국 이 실험과 같은 상태 파일과 결정 로직을 CDN 앞(엣지 함수, 가중치 오리진)이나 셸의 BundleLoader 구현에 넣게 됩니다. 배포 채널이라는 개념 자체는 Toss 내부 인프라의 몫으로 보입니다.

정리하면 granite 는 "번들을 올리고 내려받는 길"을 주고, 카나리와 블루그린 같은 "트래픽을 가르는 규칙"은 어느 쪽을 쓰든 직접 만듭니다. 그 규칙이 이 실험의 deploymentClient.js 와 서버의 deployment.json 이고, 이 부분은 Re.Pack 이든 granite 든 그대로 이식됩니다.

## 보안에 대해

이 실험은 로컬 전용이라 뺀 것이 둘 있고, 실서비스에서는 반드시 있어야 합니다.

- 배포 제어 API 인증. 이 서버의 /control 은 인증이 없습니다. 실서비스에서 이 엔드포인트는 배포 권한 체계 뒤에 있어야 합니다.
- 번들 무결성 검증. 원격 번들은 앱 서명 바깥에서 오는 코드입니다. Re.Pack 은 CodeSigningPlugin 으로 번들에 서명하고 ScriptManager 가 검증하는 경로를 제공합니다. CDN 이 탈취되면 임의 코드가 앱에서 실행되는 구조이므로, https 만으로는 부족하고 번들 서명까지가 세트입니다.

저장소에는 키, 토큰, 실데이터가 없습니다. 서버 주소는 에뮬레이터 전용 로컬 주소(10.0.2.2, localhost)뿐입니다.

## 재현 방법

```bash
# 1. v1 은 05 의 빌드 산출물을 그대로 씁니다 (05 재현 방법 참고)
# 2. v2 피처와 배포 호스트 빌드
cd feature-cart-v2 && npm run bundle:android
cd ../host-shell && npm run bundle:android

# 3. 호스트 번들을 05 네이티브 앱에 넣고 설치
cp build/index.android.bundle ../../05-repack-federation/android/app/src/main/assets/
cd ../../05-repack-federation/android && ./gradlew installDebug -PabiFilters=arm64-v8a

# 4. 배포 서버
node ../../07-deployment/server/deploy-server.js   # 4200 포트

# 5. 전환해 가며 앱 재시작
curl -X POST 'localhost:4200/control?feature=featureCart&active=green'
curl -X POST 'localhost:4200/control?feature=featureCart&strategy=canary&ratio=30'
curl localhost:4200/__log   # 실제로 어느 버전이 내려갔는지
```

05 로 돌아가려면 05 host 의 번들을 다시 assets 에 넣으면 됩니다.

## 한계

- 검증은 Android 에뮬레이터에서 했습니다. 결정 로직과 서버는 플랫폼 중립이고 05에서 iOS 동작을 확인했으므로 구조는 같지만, 07 의 수치와 스크린샷은 Android 것입니다.
- 사용자 10명을 한 화면에 그려 버킷 분포를 보였을 뿐, 실제 다수 기기 분포는 통계적으로만 성립합니다.
- 카나리에서 지표를 보고 비율을 올리는 자동화(점진 승급, 자동 롤백)는 다루지 않았습니다. 그건 배포 시스템의 영역이고, 이 실험은 그 시스템이 조작할 손잡이(deployment.json)까지를 만들었습니다.
