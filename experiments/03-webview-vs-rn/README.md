# 웹뷰와 RN, 무엇이 다른가

같은 앱 안에 같은 화면을 웹뷰로 한 번, RN 으로 한 번 만들어서 나란히 쟀습니다.

```
web/            localhost:3000 으로 뜨는 페이지
rn/             같은 화면의 RN 버전
android/        두 방식을 모두 띄우고 시간을 재는 호스트 앱
ios/            같은 앱의 iOS 판
bench.sh        Android 반복 측정
bench-ios.sh    iOS 반복 측정
```

기준: RN 0.76.9, Old Architecture, Hermes
측정: Pixel 9 에뮬레이터(API 36, arm64, RAM 4GB), iPhone 15 시뮬레이터(iOS 17.5)
조건당 10회, 중앙값
최종 확인일: 2026-08-08

**iOS 숫자는 정확하지 않습니다.** 시뮬레이터는 호스트 맥의 CPU 로 돌고 WebKit 과 Hermes 가
실기기와 다른 환경에서 실행됩니다. 절대값을 인용하지 마세요. 조건 사이의 방향만 보면 됩니다.
Android 도 에뮬레이터라 같은 한계가 있지만, 그쪽은 arm64 시스템 이미지라 조금 낫습니다.

## 결론 먼저

**릴리스 빌드에서는 RN 이 두 조건 모두 빨랐고, 디버그 빌드에서는 웹뷰가 두 조건 모두 빨랐습니다.**
빌드 타입 하나로 결론이 뒤집힙니다.

| 탭 → 첫 페인트 (중앙값) | Android debug | Android release | iOS release |
|---|---|---|---|
| 웹뷰, 프리워밍 없음 | 544 ms | 356 ms | 358 ms |
| 웹뷰, 프리워밍 있음 | 225 ms | 176 ms | 295 ms |
| RN, preload 없음 | 767 ms | 246 ms | 175 ms |
| RN, preload 있음 | 484 ms | 143 ms | 114 ms |

iOS 는 시뮬레이터라 절대값을 믿으면 안 되지만, 릴리스 Android 와 방향은 같습니다.
RN 이 두 조건 모두 빨랐고 프리워밍이 양쪽 다 효과가 있었습니다.

디버그에서 RN 이 불리한 이유는 분명합니다. Gradle 이 `react-android` 의 **debug 변종**을
가져오는데 그쪽 `libreactnative.so` 는 심볼이 안 벗겨져서 20.5MB 입니다. 여기에
디버그 앱이면 켜지는 `-Xcheck:jni` 가 JNI 호출마다 검사를 겁니다. 웹뷰는 Chromium 이
OS 안에 있어서 우리 앱의 빌드 타입에 거의 영향을 안 받습니다.

**웹뷰와 RN 을 비교할 때 디버그 숫자를 쓰면 안 됩니다.** 이 실험에서 가장 실용적인 발견입니다.

## 뜨는 과정이 다릅니다

두 방식이 화면을 띄우기까지 하는 일입니다.

```
[웹뷰]                              [RN]
Activity + WebView 뷰 생성          Activity 생성
        ↓                                   ↓
Chromium 초기화                     JS 스레드 생성, Hermes 부팅
 (provider 로딩, 렌더러 프로세스)     (인스턴스가 없을 때만)
 프로세스에서 첫 회만                        ↓
        ↓                           번들 로드
URL 요청 → 네트워크 → HTML 수신       (앱 assets 에서, 바이트코드라 파싱 없음)
        ↓                                   ↓
HTML 파싱 → DOM                     번들 실행 (모든 모듈의 최상위 코드)
CSS 파싱 → CSSOM                            ↓
레이아웃 → 페인트                    AppRegistry.runApplication
        ↓                                   ↓
JS 실행                             React 렌더 → UIManager 명령
                                            ↓
                                    네이티브 뷰 생성
```

한 줄로 줄이면 이렇습니다.

- **웹뷰는 런타임이 OS 에 있고 콘텐츠가 서버에 있습니다.**
- **RN 은 런타임도 콘텐츠도 앱 안에 있습니다.**

여기서 나머지가 전부 따라 나옵니다. 앱 용량, 배포 주기, 오프라인 동작, 진입 시간의
성격까지요.

## 앱 용량

릴리스 arm64 APK 18.2MB 를 열어 봤습니다.

| | 크기 |
|---|---|
| 웹뷰 | **0** |
| RN `lib/arm64-v8a/*.so` 합계 | 11.4 MB |
| RN `classes*.dex` 합계 | 12.3 MB |
| RN JS 번들 | 810 KB |

APK 안에 webkit 이나 chromium 이 들어간 항목은 0개입니다. `android.webkit.WebView` 는
OS 가 제공하고, `app/build.gradle` 에 의존성 한 줄도 추가하지 않습니다.

RN 쪽 큰 덩어리는 `libreactnative.so` 6.5MB, `libhermes.so` 2.3MB,
`libc++_shared.so` 1.3MB 입니다.

## 프리워밍은 양쪽 다 효과가 있습니다

붙여 놓고 보면 같은 아이디어입니다. 첫 진입이 느린 이유가 렌더가 아니라 런타임 부팅이라,
그 부팅을 미리 끝내 두는 것입니다.

| | 프리워밍 없음 | 있음 | 감소 |
|---|---|---|---|
| 웹뷰 (Android release) | 356 ms | 176 ms | 51% |
| RN (Android release) | 246 ms | 143 ms | 42% |
| 웹뷰 (iOS) | 358 ms | 295 ms | 18% |
| RN (iOS) | 175 ms | 114 ms | 35% |

웹뷰 프리워밍에서 비싼 것은 뷰 객체가 아니라 그 뒤의 브라우저 엔진 초기화입니다.
Android 는 WebView provider 로딩과 렌더러 프로세스 기동이 프로세스 단위로 한 번
일어나서, 아무 WebView 나 하나 만들어 두면 그 뒤로 싸집니다.

**같은 프리워밍인데 iOS 는 효과가 훨씬 작았습니다(18% vs 51%).** iOS 는 `WKProcessPool`
을 명시적으로 공유해야 콘텐츠 프로세스를 재사용합니다. 이 실험은 pool 을 넘겨 뒀는데도
차이가 작습니다. WebKit 쪽 초기화 비용이 Chromium 만큼 크지 않거나, 시뮬레이터에서
호스트 프로세스가 이미 따뜻해서 그럴 수 있습니다. 원인은 확인 못 했습니다.
같은 이름의 최적화라도 플랫폼마다 효과가 다르다는 것까지가 이 실험으로 말할 수 있는
범위입니다.

프리워밍 코드는 `android/.../web/WebViewWarmer.kt` 와 `ios/Bench/WebViewWarmer.swift` 입니다.

이 실험에서는 웹뷰 프리워밍을 **엔진까지만** 했습니다. 페이지까지 미리 받아 두면
화면이 이미 그려진 상태라 "탭 → 첫 페인트"가 0 에 가깝게 나오는데, RN preload
(런타임만 준비하고 렌더는 진입 때)와 조건이 달라져서 비교가 성립하지 않습니다.

## 네이티브 호출 하나에 드는 코드

같은 기능(호스트 정보 가져오기)을 양쪽에 만들었습니다.

RN 은 이게 전부입니다.

```js
const info = await Bench.getHostInfo();
```

웹뷰는 이만큼이 앱 코드입니다. 요청 ID 발급, 콜백 테이블, 타임아웃, 플랫폼별 전송 경로가
프레임워크에 없어서 직접 만들어야 합니다.

```js
const pending = new Map();
let seq = 0;

function send(type, payload) {
  const message = JSON.stringify({type, ...payload});
  if (window.AndroidBridge) {
    window.AndroidBridge.postMessage(message);
  } else if (window.webkit && window.webkit.messageHandlers.iosBridge) {
    window.webkit.messageHandlers.iosBridge.postMessage(message);
  }
}

function request(type, payload = {}) {
  const id = String(++seq);
  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      pending.delete(id);
      reject(new Error('네이티브 응답 없음'));
    }, 3000);
    pending.set(id, {resolve, timer});
    send(type, {...payload, id});
  });
}

window.__resolve = function (id, json) {
  const entry = pending.get(id);
  if (!entry) return;
  clearTimeout(entry.timer);
  pending.delete(id);
  entry.resolve(JSON.parse(json));
};
```

네이티브 쪽도 마찬가지입니다. RN 은 `@ReactMethod` 를 붙이면 끝인데, 웹뷰는 JSON 을
파싱해서 문자열 `type` 으로 분기하고, 응답을 JS 문자열로 만들어 주입해야 합니다.

```kotlin
// 웹뷰
webView.evaluateJavascript("window.__resolve('$id', ${JSONObject.quote(payload)})", null)
```

이스케이프를 잘못하면 컴파일도 되고 실행도 되는데 조용히 깨집니다.

기능 하나면 감당할 만합니다. 서너 개가 되면 프로토콜을 직접 설계하고 버전 관리해야 하고,
웹과 앱의 배포 주기가 달라서 구버전 앱이 신버전 웹을 여는 조합을 항상 다뤄야 합니다.
이게 웹뷰의 숨은 비용입니다.

## 기능이 늘어나면 어떻게 되나

지금 양쪽에 만든 기능은 세 개입니다. 첫 페인트 신호, 호스트 정보 조회, 결과 반환.
그 상태의 실제 코드 줄 수입니다. 주석과 빈 줄은 뺐습니다.

| | JS 쪽 | 네이티브 쪽 | 합계 |
|---|---|---|---|
| 웹뷰 | 28줄 | 39줄 | 67줄 |
| RN | 14줄 | 40줄 | 54줄 |

숫자만 보면 큰 차이가 아닌 것 같은데, 안을 갈라 보면 성격이 다릅니다.

**웹뷰의 28줄은 기능이 0개여도 필요한 배관입니다.** 요청 ID 발급, 콜백 테이블,
타임아웃, 플랫폼별 전송 경로. 기능을 하나도 안 만들어도 저 코드는 있어야 합니다.
RN 쪽에서 그 자리에 해당하는 코드는 0줄입니다. 프레임워크 안에 있습니다.

기능 하나를 더 붙일 때 드는 비용도 다릅니다.

| 기능 하나 추가 | 웹뷰 | RN |
|---|---|---|
| 네이티브 | `when` 에 분기 하나, JSON 파싱, 응답을 JS 문자열로 주입 | `@ReactMethod` 하나 |
| JS | 래퍼 함수 하나 (`request('TYPE')` 호출) | `export function` 하나 |
| 타입 | 없음. 문자열 `type` 과 JSON 키로 맞춤 | 인자와 반환이 시그니처로 고정 |
| 실수했을 때 | 컴파일 통과, 런타임에 조용히 실패 | 시그니처 불일치가 드러남 |

**줄 수보다 중요한 건 프로토콜이 제품이 된다는 점입니다.** 기능이 서너 개를 넘으면
`type` 문자열 목록과 payload 스키마를 문서로 관리해야 하고, 웹과 앱의 배포 주기가 달라서
구버전 앱이 신버전 웹을 여는 조합을 항상 다뤄야 합니다. 웹은 오늘 배포하고 앱은 다음 주에
심사를 통과하니까요. 그래서 모든 메시지에 버전 필드를 넣고 앱 버전별 분기를 치게 됩니다.

RN 은 JS 번들과 네이티브가 같이 배포돼서 이 문제가 없습니다. OTA 를 붙이는 순간
같은 문제가 생기지만, 그때도 인터페이스가 타입으로 고정돼 있어서 표면이 좁습니다.
02 번 README 의 버전 스큐 절과 같은 얘기입니다.

교차점은 대략 이렇습니다. 네이티브 기능이 한두 개면 웹뷰 배관이 감당할 만합니다.
서너 개를 넘어가면 브리지 프로토콜 자체를 설계하고 버전 관리하는 일이 시작되고,
그때부터는 RN 이 유리해집니다.

## SSR, 검색 노출, 공유 링크

성능 표보다 커머스에서 더 자주 결론을 가르는 축입니다.

**RN 화면에는 URL 이 없습니다.** 이 한 줄에서 아래가 전부 따라 나옵니다.

| | 웹뷰 | RN |
|---|---|---|
| 검색 노출 | 같은 URL 을 웹에서도 서빙하면 크롤링됩니다 | 불가능합니다 |
| 공유 미리보기 | OG 태그를 내려주면 카카오톡과 슬랙에 썸네일이 뜹니다 | 불가능합니다 |
| 딥링크 | URL 이 그대로 주소입니다 | 가능하지만 URL 에서 화면으로 가는 라우팅을 직접 만들어야 합니다 |
| SSR | 서버가 콘텐츠를 채운 HTML 을 내려줍니다 | 개념이 없습니다. 번들이 앱 안에 있습니다 |

**실무에서 이게 결정적인 이유는 화면을 두 번 만들게 되기 때문입니다.** 상품 상세를
RN 으로 만들어도, 링크 공유와 검색 노출을 위해 같은 내용의 웹 페이지가 어차피 필요합니다.
그러면 같은 화면이 두 벌이 되고 계속 어긋납니다. 웹뷰로 만들면 앱과 웹이 같은 페이지를
씁니다. "상품 상세는 웹뷰"라는 판단의 진짜 근거는 성능이 아니라 대개 이쪽입니다.

**SSR 은 웹뷰 안에서만 의미가 있는 축입니다.** 그리고 이 실험의 숫자에 직접 영향을 줍니다.
우리가 잰 페이지는 서버가 완성된 HTML 을 내려주는 정적 파일이라, 조건상 SSR 과 같습니다.
첫 HTML 에 콘텐츠가 이미 들어 있어서 파싱하면 바로 그릴 수 있습니다.

같은 화면을 CSR 로 만들었다면 HTML 을 받고, JS 번들을 또 받고, 실행한 뒤에야 콘텐츠가
나타납니다. 웹뷰 숫자는 그만큼 더 나빠집니다. 이 실험은 **웹뷰에 유리한 조건**에서 쟀는데도
릴리스에서 RN 이 빨랐다는 뜻이기도 합니다.

## 웹뷰 대비 RN 의 장단점

### RN 이 나은 점

**네이티브 뷰를 그립니다.** `<Text>` 가 실제 `TextView` 가 됩니다. 스크롤 관성, 폰트
렌더링, 접근성, 키보드 대응이 OS 기본값과 같습니다. 웹뷰는 그 위에서 흉내를 냅니다.

**네이티브 기능 접근이 짧습니다.** 위 코드 비교가 그대로 답입니다. 생체인증, 카메라,
푸시 권한처럼 OS API 를 여러 개 쓰는 화면일수록 격차가 벌어집니다.

**오프라인에 강합니다.** 번들이 앱 안에 있어서 네트워크가 없어도 화면이 뜹니다.
웹뷰는 캐시 전략을 따로 설계해야 하고, 그게 웹뷰 최적화 작업의 큰 축입니다.

**릴리스 진입이 빨랐습니다.** 이 측정에서는 preload 없이도 246ms 로 웹뷰 356ms 보다
빨랐습니다. 번들이 로컬에 있고 Hermes 바이트코드라 파싱 단계가 없기 때문입니다.

**JS 컨텍스트가 유지됩니다.** 화면을 닫아도 살아 있어서 두 번째 진입이 빠릅니다.
웹뷰는 화면을 닫으면 컨텍스트도 사라집니다. 다만 이건 아래 단점이기도 합니다.

### RN 이 못한 점

**앱 용량이 늘어납니다.** 이 측정에서 arm64 기준 `.so` 11.4MB 에 dex 와 번들이 더
붙습니다. 웹뷰는 0 입니다. 화면 하나 붙이자고 치르기엔 큰 값입니다.

**배포가 스토어에 묶입니다.** 웹뷰는 서버에 올리면 끝입니다. RN 은 번들이 앱 안에 있어서
OTA 를 따로 붙여야 하고, 그것도 스토어 정책 안에서만 됩니다.

**웹과 코드를 공유하지 못합니다.** 상품 상세를 웹에서도 보여줘야 하면 웹뷰는 같은
페이지를 재사용합니다. RN 은 화면을 두 번 만들게 됩니다.

**URL 이 없습니다.** 검색 노출과 공유 미리보기가 안 됩니다. 위 절에 자세히 적었습니다.
커머스에서는 이게 성능보다 먼저 결론을 가르는 경우가 많습니다.

**JS 컨텍스트 공유가 부작용을 만듭니다.** 화면을 닫아도 스토어 상태, 타이머, 구독이
살아남습니다. unmount 정리를 명시적으로 안 하면 두 번째 진입에서 이전 상태가 보이거나
이벤트가 두 번 발화합니다. 01 번에서도 같은 지점을 짚었습니다.

**빌드와 도구가 무겁습니다.** Node, Metro, watchman 이 필요하고 앱 빌드 시간이 늘어납니다.
02 번은 그 비용을 SDK 로 격리하는 실험이었습니다.

**preload 는 메모리를 상주시킵니다.** 인스턴스가 계속 살아 있어서 저사양 기기에서
백그라운드 kill 확률이 올라갑니다. 웹뷰 프리워밍도 같은 문제를 갖지만 정도가 덜합니다.

## 화면별로 어디를 쓰나

측정값보다 이쪽이 실제 판단에 가깝습니다. 성능 차이가 100ms 대라면 그건 결정 요인이
아닙니다. 무엇이 자주 바뀌고 무엇이 OS 를 깊게 쓰는지가 가릅니다.

| 화면 | 선택 | 이유 |
|---|---|---|
| 약관, FAQ, 공지 | 웹뷰 | 텍스트뿐이고 자주 바뀝니다 |
| 이벤트, 프로모션 | 웹뷰 | 기간제입니다. 심사 기다리면 이벤트가 끝납니다 |
| 상품 상세 | 웹뷰 + 네이티브 하단바 | 마케팅이 매일 고치고, 웹 공유 링크와 페이지를 공유합니다 |
| 결제 | 웹뷰 | PG 와 카드사 인증이 웹뷰를 요구합니다. 선택지가 없습니다 |
| 홈 피드, 상품 목록 | RN | 무한 스크롤과 이미지 수백 장 |
| 채팅, 문의 | RN | 키보드 대응, 역방향 스크롤, 첨부 |
| 장바구니 | RN | 수량 조절 즉각 반응, 스와이프 삭제 |
| 카메라, QR | RN | 권한과 프레임 제어 |
| 설정 | RN | 토글, 생체인증, 푸시 권한이 전부 OS API |

경계선에 있는 예가 리뷰 목록입니다. 상세 안에 요약 5개면 웹뷰로 충분하고, 전용 화면에서
무한 스크롤과 사진 그리드에 풀스크린 이미지 뷰어 전환까지 하면 RN 이 맞습니다.
웹뷰 안에서는 그 전환이 웹뷰 경계를 넘지 못합니다.

실무에서 제일 흔한 건 섞는 것입니다. 상품 상세의 콘텐츠는 웹뷰, 하단 구매 버튼은 네이티브로
올립니다. 대신 웹뷰의 스크롤 위치를 네이티브가 알아야 해서 스크롤 이벤트를 브리지로
계속 흘려보내야 하는데, 초당 수십 번이라 throttle 없이 하면 그 자체가 렉의 원인입니다.

# 웹 페이지 서버

릴리스로 재려면 `assembleRelease` 후 서명해서 설치하고
`BENCH_PKG=com.example.bench ./bench.sh 10` 으로 돌립니다.

## 측정 방법에 대해

두 방식을 같은 자로 재는 게 이 실험의 절반입니다.

시작점은 네이티브가 화면 전환을 시작한 시각입니다. 끝점은 콘텐츠가 화면에 나간 직후
JS 가 알려 온 시각입니다. 웹뷰는 `requestAnimationFrame` 두 번, RN 은
`InteractionManager` 뒤에 `requestAnimationFrame` 두 번에서 신호를 보냅니다.
둘 다 "이 프레임이 나간 다음"이라는 같은 뜻입니다.

`onPageFinished` 나 컴포넌트 mount 를 끝점으로 잡으면 두 방식의 정의가 어긋나서
숫자를 비교할 수 없습니다.

화면 구성도 맞췄습니다. 섹션 4개, 행 6개, 버튼 2개로 같습니다.

측정값을 뽑는 경로는 플랫폼마다 다릅니다. 스크린샷을 읽어 옮기면 반복이 안 되고
편차도 못 냅니다.

| | 조건 전달 | 결과 수집 |
|---|---|---|
| Android | `am start --es auto webview --ez warm false` | `adb logcat -s BENCH` |
| iOS | launch arguments (`-auto webview -warm 0`) | `simctl launch --console-pty` stdout |

iOS 쪽이 이렇게 된 이유는 시뮬레이터 창을 GUI 로 자동화하려다 실패했기 때문입니다.
02 번에서 `System Events` 로 창을 잡으려다 못 잡았습니다. launch arguments 는
`UserDefaults` 가 `-key value` 형태를 그대로 읽어 주고, stdout 은 `--console-pty` 로
받을 수 있어서 창을 건드리지 않고 끝납니다.

프리워밍 조건에서는 고정 시간을 기다리지 않고 런타임이 실제로 준비됐는지 확인하고
누릅니다. 처음에는 4초 고정으로 했는데 preload 가 덜 끝난 채로 눌러서 10회 중 3회가
cold 로 기록됐습니다.

## 확인한 것과 안 한 것

Android 에뮬레이터에서 debug 와 release 각각 4조건 10회씩 80회,
iOS 시뮬레이터에서 release 4조건 10회씩 40회, 총 120회 측정했습니다.
화면 렌더는 양쪽 다 눈으로 확인했습니다.

안 한 것입니다.

- 실기기. 에뮬레이터와 시뮬레이터는 호스트 CPU 를 쓰기 때문에 절대값이 실기기와 다릅니다.
  순서는 뒤집히지 않을 것으로 보지만 확인은 안 했습니다
- **iOS 숫자의 신뢰도가 특히 낮습니다.** 시뮬레이터는 아키텍처 변환 없이 호스트에서
  네이티브로 도는데다, WebKit 이 macOS 쪽 구현을 일부 공유합니다.
  Android 는 arm64 시스템 이미지라 그나마 실기기에 가깝습니다.
  iOS 는 "RN 이 더 빨랐다"는 방향까지만 쓰고, 358ms 같은 숫자는 인용하지 마세요
- iOS 의 debug 빌드. Android 에서 결론을 뒤집었던 변수인데 iOS 는 release 만 쟀습니다
- iOS 앱 용량. 시뮬레이터 `.app` 이 28MB 인데 슬라이스가 여러 개 들어가 있어서
  배포 크기와 비교가 안 됩니다. 실기기 아카이브로 다시 재야 합니다
- iOS 웹뷰 프리워밍의 효과가 왜 작은지. 18% 라는 것만 확인했고 원인은 못 밝혔습니다
- 캐시를 켠 웹뷰. 지금은 `LOAD_NO_CACHE` 로 조건을 통제했습니다.
  실무 웹뷰 최적화의 큰 축이라 따로 잴 값어치가 있습니다
- 스크롤 성능과 메모리. 진입 시간만 쟀습니다. 화면별 판단 표의 근거인
  "무한 스크롤에서 웹뷰가 불리하다"는 이 실험으로 확인한 것이 아닙니다
- 네트워크가 느린 환경. localhost 라 사실상 네트워크 지연이 0 입니다.
  실제 웹뷰는 여기서 더 불리해집니다
- CSR 웹뷰. 잰 페이지는 완성된 HTML 을 내려주는 정적 파일이라 조건상 SSR 과 같습니다.
  SPA 로 만들면 웹뷰 숫자가 더 나빠집니다
- 기능 개수에 따른 실제 곡선. 기능 3개 시점의 줄 수만 셌고, 20개까지 늘려 본 것이 아닙니다.
  그 이후의 얘기는 프로토콜 관리 비용에 대한 판단이지 측정이 아닙니다
